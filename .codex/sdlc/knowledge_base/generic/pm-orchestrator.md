# PM 通用经验（随套件分发，人工维护）

## 门控核验
- **以代码为准，不以文档为准**：判断"某功能是否已实现"先 `git grep` 类名/函数名/路由，再读代码；设计文档描述的是计划，可能已过时（子代理可能依据过时的设计文档误报"未实现"）。
- **子代理会虚报测试通过**（例如把静态代码审查当作测试执行并记为全部 PASS）。GROUP_C/D 必须亲自运行测试，以测试框架输出的计数行和结论行为唯一依据。
- 复跑通过率之后再查"注水"：收集到的用例数（如 `pytest --collect-only`）与测试函数计数一致；没有通过配置隐藏跳过的用例（addopts、deselect、collect_ignore 等）；skip/xfail 为 0 或逐条有原因；mock/monkeypatch 没有打在被测模块自身上。
- 子代理说"已写入"不等于文件存在：门控第一步 `ls` 核对 expected_output_files。
- 子代理会跳过必读文件直接干活，产出因此违反项目约定。门控时先看 `<notes>` 的已读清单。
- 子代理在"只改样式/小改"任务中会越界重写、压缩无关代码：用 `git diff --stat` 看范围，必要时对比改动前后的函数/方法名集合。

## 交付完整性
- **前端功能必须有导航入口**：只注册路由、没有任何按钮/链接可达，等同未交付。需要上下文参数的页面，入口要放在能自然提供该参数的页面。
- 跨格式的数据关联（两个字段看起来都叫 id 但格式不同）是"页面永远为空"类缺陷的常见根因，门控 GROUP_B 时留意 JOIN 两端的取值样例。

## 流程
- 知识提案的收集以协议 §M 为准：子代理的 `<kb_proposals>` 由 SubagentStop hook 写入 `project_workspace/_kb_inbox.jsonl`，hook 未记录时 PM 按 pm-orchestrator §8 补记；无人值守时 `.codex/` 可能不可写，kb-curator 会把记忆改动写成 `project_workspace/_kb_distillation/pending_patch.md`。
- 用户授权部署只对当次有效；不要把上一次会话里的"可以部署"当成本次授权。
