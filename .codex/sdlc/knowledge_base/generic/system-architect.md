# 架构通用经验（随套件分发，人工维护）

- 已被约束决定的事项写 constraint-driven ADR，不要伪造"对等候选方案"；真正要选择的才做 ≥2 方案对比。
- 引用现有代码前用 `git grep -n` / `ls` 核实，最常见的门控失败是引用了不存在或已改名的类/文件。
- 接口契约里写清列表还是单对象、单数还是复数字段名、分页方式；这类细节是前后端/测试联调失败的主要来源。
- 超大表（千万级）上的设计要写明分批处理与索引策略。
- 资源受限的部署目标（小内存设备、单机）要在 NFR 与风险中显式考虑：批量大小、并发 worker 数、超时。
- 异步任务设计要写明：超时（软超时可被捕获，OOM 的 SIGKILL 不能）、重试策略与最终失败状态，避免任务永久停在"处理中"。
- 【适用：x86_64 上的本地推理】预编译的 onnxruntime / PyTorch wheel 通常要求 AVX2，老 CPU 上会 SIGILL：进程直接崩溃、不可捕获、绕过所有降级设计，且开发机测不出。目标机上用"import + 一次真实推理"的探针验证，同一运行时的多个使用方合并评估。
- 【适用：浏览器流式推送】优先 SSE：走普通 HTTP、可带 Authorization 头；浏览器 WebSocket 无法设置该头，凭据只能放进 URL 而被访问日志记录。所有端点都禁止 `?token=` 传凭据。
